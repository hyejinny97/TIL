# ✔ 응용 계층

## 1️⃣ DNS와 자원

### 도메인 네임과 네임 서버

- 도메인 네임: 문자열 형태의 호스트 특정 정보
- 네임 서버 (DNS 서버): 도메인 네임과 IP 주소를 관리하는 서버
- 도메인 네임을 네임 서버에 질의하면, 이에 대한 IP 주소를 알 수 있음
- 도메인 네임은 IP 주소에 비해 기억하기 쉬울뿐더러, IP 주소가 바뀌더라도 바뀐 IP 주소에 도메인 네임을 다시 대응하면 되므로 IP 주소만으로 호스트를 특정하는 것보다 더 간편함

#### 도메인 네임

```
www.example.com.
```

- 전체 주소 도메인 네임 (FQDN, Fully-Qualified Domain Name): 도메인 네임을 모두 포함하는 도메인 네임
  - ex) www.example.com.
  - FQDN의 첫 번째 부분을 호스트 네임이라 부르기도 함

##### 루트 도메인

- ex) .
- 마지막에 점이 찍힌 형태

##### 최상위 도메인

- ex) com
- Top Level Domain, TLD

##### 2단계 도메인

- ex) example

##### 3단계 도메인 등

- ex) www

#### 네임 서버

- 계층적인 도메인 네임을 효율적으로 관리하기 위해 네임 서버 또한 계층적인 형태를 이룸
- 네임 서버는 여러 개 존재하며 전 세계 여러 군데에 위치해 있음
- DNS (Domain Name System): 계층적이고 분산된 도메인 네임에 대한 관리 체계

### 계층적 네임 서버

- '도메인 네임을 풀이(resolve) 한다' === '도메인 네임에 대응되는 IP 주소를 알아낸다'

#### 네임 서버의 유형

##### 1. 로컬 네임 서버

- 클라이언트와 맞닿아 있는 네임 서버
- 클라이언트가 도메인 네임을 통해 IP 주소를 알아내고자 할 때 가장 먼저 찾게 되는 네임 서버
- ISP에서 로컬 네임 서버의 주소를 할당해줄 수도 있고, 공개 DNS 서버를 이용할 수도 있음
  - ex) 구글의 8.8.8.8, 클라우드플레어의 1.1.1.1
- IP 주소를 알고 있다면 그 IP 주소를 알려 주고, 모른다면 루트 네임 서버에게 질의하게 됨

##### 2. 루트 네임 서버

- 루트 도메인을 관장하는 네임 서버
- 질의에 대해 TLD 네임 서버의 IP 주소를 반환할 수 있음

##### 3. TLD 네임 서버

- TLD를 관리하는 네임 서버
- 질의에 대해 TLD의 하위 도메인 네임을 관리하는 네임 서버 주소를 반환할 수 있음

##### 4. 책임 네임 서버

- 특정 도메인 영역을 관리하는 네임 서버
- 다른 네임 서버에게 떠넘기지 않고 곧바로 답할 수 있는 네임 서버
- 즉, 일반적으로 로컬 네임 서버는 책임 네임 서버로부터 원하는 IP 주소를 얻어내

#### 로컬 네임 서버가 네임 서버들에게 질의하는 방법

##### 1. 재귀적 질의

- 클라이언트가 로컬 네임 서버에게 도메인 네임을 질의하면, 로컬 네임 서버가 루트 네임 서버에게 질의하고, 루트 네임 서버가 TLD 네임 서버에게 질의하고, TLD 네임 서버가 다음 단계에 질의하는 과정을 반복하며 최종 응답 결과를 역순으로 전달받는 방식

##### 2. 반복적 질의

- 클라리언트가 로컬 네임 서버에게 도메인 네임을 질의하면, 로컬 네임 서버는 루트 도메인 서버에게 질의해서 다음으로 질의할 네임 서버의 주소를 응답받고, 다음으로 TLD 네임 서버에게 질의해서 다음으로 질의할 네임 서버의 주소를 응답받는 과정을 반복하다가 최종 응답 결과를 클라이언트에게 알려 주는 방식

#### DNS 캐시

- 재귀적 질의든 반복적 질의든, 하나의 도메인 네임을 리졸빙하기 위해 8개의 단계를 거쳐야 함
- 이는 시간이 오래 걸리고 네트워크상의 메시지 수가 지나치게 늘어날 수 있을 뿐 아니라 네임 서버에 과부하가 발생할 수도 있음
- DNS 캐시: 네임 서버들이 기존에 응답받은 결과를 임시로 저장했다가 추후 같은 질의에 이를 활용하는 방식
  - 임시 저장된 값은 TTL (Time To Live) 값과 함께 저장되어, TTL만큼의 시간동안만 임시로 저장됨
- DNS 캐시를 이용하면 짧은 시간 안에 원하는 IP 주소를 얻어낼 수 있음

### 자원을 식별하는 URI

- 자원
  - 네트워크상의 메시지를 통해 주고받는 대상
  - 송수신하고자 하는 정보
  - HTTP 요청 메시지의 대상
  - ex) HTML 파일, 이미지, 동영상 파일 등
- URI: 자원을 식별할 수 있는 정보
  1. URL (Uniform Resource Locator): '위치'를 이용해 자원을 식별
  2. URN (Uniform Resource Name): '이름'을 이용해 자원을 식별

#### URL

```
foo://www.example.com:8042/over/there?name=ferret#nose
```

##### scheme

- URL의 첫 부분
- 자원에 접근하는 방법
- 일반적으로 사용할 프로토콜이 명시됨
- ex) http, https

##### authority

- 호스트를 특정할 수 있는 정보
- IP 주소 또는 도메인 네임
- 콜론 뒤에 포트 번호를 덧붙일 수도 있음
- ex) www.example.com:8042

##### path

- 자원이 위치한 경로
- ex) /over/there

##### query

- 쿼리 문자열(쿼리 파라미터): 물음표로 시작되는 '키=값' 형태의 데이터로, 앰퍼샌드(&)를 사용하여 여러 쿼리 문자열을 연결할 수 있음
- ex) ?name=ferret&sort=asc

##### fragment

- 자원의 한 조각을 가리키기 위한 정보
- 흔히 HTML 파일과 같은 자원에서 특정 부분을 가리키기 위해 사용됨
- ex) #nose

#### URN

- 자원의 위치가 변경되면 기존 URL로는 자원을 식별할 수 없게 됨
- 반면, URN은 자원에 고유한 이름을 붙이는 이름 기반 식별자이기에 자원의 위치와 무관하게 자원을 식별할 수 있음

### cf) DNS 레코드 타입

- 네임 서버는 DNS 자원 레코드라 불리는 정보를 저장하고 관리함

  | 타입  | 이름            | 값          | TTL |
  | ----- | --------------- | ----------- | --- |
  | A     | example.com     | 1.2.3.4     | 300 |
  | CNAME | www.example.com | example.com | 300 |

- 레코드 유형

  | 레코드 유형(타입) | 설명                                                     |
  | ----------------- | -------------------------------------------------------- |
  | A                 | 특정 호스트에 대한 도메인 네임과 IPv4 주소와의 대응 관계 |
  | AAA               | 특정 호스트에 대한 도메인 네임과 IPv6 주소와의 대응 관계 |
  | CNAME             | 호스트 네임에 대한 별칭 지정                             |
  | NS                | 특정 호스트의 IP 주소를 찾을 수 있는 네임 서버           |
  | MX                | 해당 도메인과 연동되어 있는 메일 서버                    |

## 2️⃣ HTTP

### HTTP의 특성

- Hypertext Transfer Protocol
- 응용 계층에서 정보를 주고받는 데 사용되는 프로토콜

#### 1. 요청-응답 기반 프로토콜

- HTTP는 클라이언트-서버 구조 기반의 요청-응답 프로토콜임

#### 2. 미디어 독립적 프로토콜

- 클라이언트는 HTTP 요청 메시지를 통해 서버의 자원을 요청할 수 있고, 서버는 HTTP 응답 메시지로 요청받은 자원에 대해 응답할 수 있음
- HTTP를 통해서 HTML, JPEG, PNG, JSON, XML, PDF 파일 등 다양한 종류의 자원을 주고받을 수 있음
- 즉, HTTP는 주고받을 자원의 특성과 무관하게 그저 자원을 주고받을 수단(인터페이스)의 역할만을 수행함

##### 미디어 타입

- 메시지로 주고받는 자원의 종류
- '타입/서브타입' 형식으로 구성됨
  - 타입 (type): 데이터 유형
  - 서브타입 (subtype): 주어진 타입에 대한 세부 유형
- 별표 문자(\*)는 여러 미디어 타입을 통칭하기 위해 사용됨
  - ex) image/\*, \*/\*
- 부가적인 설명을 위해 선택적으로 매개변수가 포함될 수도 있음
  - '타입/서브타입;매개변수=값'형식으로 표현됨

1. text 타입

   - 일반 텍스트 형식의 데이터

   | 서브타입        | 서브타입 설명     |
   | --------------- | ----------------- |
   | text/plain      | 평문 텍스트 문서  |
   | text/html       | HTML 문서         |
   | text/css        | CSS 문서          |
   | text/javascript | 자바스크립트 문서 |

2. image 타입

   - 이미지 형식의 데이터

   | 서브타입   | 서브타입 설명 |
   | ---------- | ------------- |
   | image/png  | PNG 이미지    |
   | image/jpeg | JPEG 이미지   |
   | image/webp | WebP 이미지   |
   | image/gif  | GIF 이미지    |

3. video 타입

   - 비디오 형식의 데이터

   | 서브타입   | 서브타입 설명 |
   | ---------- | ------------- |
   | video/mp4  | MP4 이미지    |
   | video/ogg  | OGG 이미지    |
   | video/webm | WebM 이미지   |

4. audio 타입

   - 오디오 형식의 데이터

   | 서브타입   | 서브타입 설명 |
   | ---------- | ------------- |
   | audio/midi | MIDI 이미지   |
   | audio/wav  | WAV 이미지    |

5. application 타입

   - 바이너리 형식의 데이터

   | 서브타입                          | 서브타입 설명                                                  |
   | --------------------------------- | -------------------------------------------------------------- |
   | application/octet-stream          | 알 수 없는 바이너리 데이터를 포함한 일반적인 바이너리 데이터   |
   | application/pdf                   | PDF 문서 형식 데이터                                           |
   | application/xml                   | XML 형식 데이터                                                |
   | application/json                  | JSON 문서 형식 데이터                                          |
   | application/x-www-form-urlencoded | HTML 입력 폼 데이터(키-값 형태의 입력값을 URL 인코딩한 데이터) |

6. multipart 타입

   - 각기 다른 미디어 타입을 가질 수 있는 여러 요소로 구성된 데이터

   | 서브타입            | 서브타입 설명       |
   | ------------------- | ------------------- |
   | multipart/form-data | HTML 입력 폼 데이터 |
   | multipart/encrypted | 암호화된 데이터     |

#### 3. 스테이트리스 프로토콜

- HTTP는 상태를 유지하지 않는 스테이스리스 프로토콜임
- 즉, 서버가 HTTP 요청을 보낸 클라이언트와 관련된 상태를 기억하지 않음
- 따라서, 모든 HTTP 요청은 기본적으로 독립적인 요청으로 간주됨
- 장점
  - 확장성이 높음: 특정 클라이언트가 특정 서버에 종속되지 않기 때문에, 언제든 쉽게 서버를 추가할 수 있음
  - 견고성이 높음: 서버 중 하나에 문제가 생겨도 쉽게 다른 서버로 대체가 가능함

#### 4. 지속 연결 프로토콜

##### HTTP 1.0 이하

- 비지속 연결
- 쓰리 웨이 핸드셰이크를 통해 TCP 연결을 수립한 후, 요청에 대한 응답을 받으면 연결을 종료하는 방식으로 동작함
- 따라서, 추가적인 요청-응답을 하기 위햐서는 다시 TCP 연결을 수립해야했음

##### HTTP 1.0 이상

- 지속 연결 (킵 얼라이브)
- 하나의 TCP 연결상에서 여러 개의 요청-응답을 주고받을 수 있음
- 이를 통해, 더 빠르게 여러 HTTP 요청-응답을 처리할 수 있게 됨

### HTTP (1.1 버전) 메시지 구조

- 시작 라인, 필드 라인(헤더 라인), 메시지 본문으로 구성됨

#### 1. 시작 라인

- HTTP 요청 메시지일 경우 시작 라인은 '요청 라인'이 되고, HTTP 응답 메시지일 경우 시작 라인은 '상태 라인'이 됨

##### 요청 라인

```
메서드 요청대상 HTTP버전
```

1.  메서드

    - 클라이언트가 서버의 자원(요청 대상)에 대해 수행할 작업의 종류
    - GET, POST, PUT, DELETE 등

2.  요청 대상

    - HTTP 요청을 보낼 서버의 자원
    - (쿼리가 포함된) URI의 경로
    - ex) /hello?q=world

3.  HTTP 버전

    - 사용된 HTTP 버전
    - ex) HTTP/1.1

##### 상태 라인

```
HTTP버전 상태코드 이유구문
```

1. 상태 코드

   - 요청에 대한 결과를 나타내는 세 자리 정수
   - ex) 200, 404

2. 이유 구문

   - 상태 코드에 대한 문자열 형태의 설명
   - ex) OK, Not Found

#### 2. 필드 라인

- 헤더 라인이라고도 부름
- 0개 이상의 HTTP 헤더가 명시됨
  - HTTP 헤더: HTTP 통신에 필요한 부가 정보
- 각 HTTP 헤더는 콜론을 기준으로 헤더 이름과 하나 이상의 헤더 값으로 구성됨
  - ex) Host: www.example.com

#### 3. 메시지 본문

- 메시지 본문은 존재하지 않을 수도 있음
- 다양한 콘텐츠 타입이 사용될 수 있음

### HTTP 메서드

| HTTP 메서드 | 설명                                              |
| ----------- | ------------------------------------------------- |
| GET         | 자원을 습득하기 위한 메서드                       |
| HEAD        | GET과 동일하나, 헤더만을 응답받는 메서드          |
| POST        | 서버로 하여금 특정 작업을 처리하게끔 하는 메서드  |
| PUT         | 자원을 대체하기 위한 메서드                       |
| PATCH       | 자원에 대한 부분적 수정을 위한 메서드             |
| DELETE      | 자원을 삭제하기 위한 메서드                       |
| CONNECT     | 자원에 대한 양방향 연결을 시작하는 메서드         |
| OPTIONS     | 사용 가능한 메서드 등 통신 옵션을 확인하는 메서드 |
| TRACE       | 자원에 대한 루프백 테스트를 수행하는 메서드       |

#### GET - 가져다주세요

- 특정 자원을 조회할 때 사용되는 메서드
- '요청 대상'에는 일반적으로 요청할 자원에 대한 쿼리가 포함된 경로가 명시됨
- 'Host 헤더'에는 요청을 보낼 호스트가 명시됨

#### HEAD - 헤더만 가져다주세요

- 서버는 요청에 대한 응답으로 응답 메시지의 헤더만을 반환함

#### POST - 처리해 주세요

- 서버로 하여금 특정 작업을 처리하도록 요청하는 메서드 (범용성이 매우 넓은 메서드)
- 주로, 클라이언트가 서버에 새로운 자원을 생성하고자 할 때 사용됨
- 처리할 대상은 흔지 메시지 본문으로 명시됨
- 서버는 응답 메시지의 Location 헤더를 통해 새로 생성된 자원의 위치를 클라이언트에게 알려 줄 수 있음

#### PUT - 덮어써 주세요

- 요청 자원이 없다면 메시지 본문으로 자원을 새롭게 생성하거나, 이미 자원이 존재한다면 메시지 본문으로 자원을 완전히 대체하는 메서드

#### PATCH - 일부 수정해 주세요

- 자원을 부분적으로 수정하고자 할 때 사용되는 메서드

#### DELETE - 삭제해 주세요

- 특정 자원을 삭제하고 싶을 때 사용하는 메서드

### HTTP 상태 코드

- 요청에 대한 결과를 나타내는 세 자리 정수
- 백의 자리수를 기준으로 유형을 구분할 수 있음

| 상태 코드        | 설명                      |
| ---------------- | ------------------------- |
| 100번대(100~199) | 정보성 상태 코드          |
| 200번대(200~299) | 성공 상태 코드            |
| 300번대(300~399) | 리다이렉션 상태 코드      |
| 400번대(400~499) | 클라이언트 에러 상태 코드 |
| 500번대(500~599) | 서버 에러 상태 코드       |

#### 200번대: 성공 상태 코드

- 요청이 성공했음을 의미

| 상태 코드 | 이유 구문  | 설명                                                    |
| --------- | ---------- | ------------------------------------------------------- |
| 200       | OK         | 요청이 성공했음                                         |
| 201       | Created    | 요청이 성공했으며, 새로운 자원이 생성되었음             |
| 202       | Accepted   | 요청을 잘 받았으나, 아직 요청한 작업을 끝내지 않았음    |
| 204       | No Content | 요청이 성공했지만, 메시지 본문으로 표시할 데이터가 없음 |

#### 300번대: 리다이렉션 상태 코드

- 리다이렉션: 클라이언트가 요청한 자원이 다른 곳에 있을 때, 클라이언트의 요청을 다른 곳으로 이동시키는 것을 의미
- 서버는 응답 메시지의 Location 헤더를 통해 요청한 자원이 위치한 URL을 안내해 줄 수 있음
- 이를 수신한 클라이언트는 Location 헤더에 명시된 URL로 즉시 재요청을 보내어 새로운 URL에 대한 응답을 받게 됨
- 304 (Not Modified): 자원이 변경되지 않았음을 의미하는 상태 코드 (캐시와 관련된 상태 코드)

##### 1. 영구적인 리다이렉션

- 자원이 완전히 새로운 곳으로 이동하여 경로가 영구적으로 재지정되는 것을 의미
- 기존의 URL에 요청 메시지를 보내면 항상 새로운 URL로 리다이렉트 됨

| 상태 코드 | 이유 구문          | 설명                                            |
| --------- | ------------------ | ----------------------------------------------- |
| 301       | Moved Permanently  | 영구적 리다이렉션: 재요청 메서드 변경될 수 있음 |
| 308       | Permanent Redirect | 영구적 리다이렉션: 재요청 메서드 변경되지 않음  |

##### 2. 일시적인 리다이렉션

- 자원의 위치가 임시로 변경되었거나 임시로 사용할 URL이 필요한 경우에 주로 사용됨
- 어떤 URL에 대해 일시적인 리다이렉션 관련 상태 코드를 응답받았다면 여전히 요청을 보낸 URL은 기억해야 함

| 상태 코드 | 이유 구문          | 설명                                            |
| --------- | ------------------ | ----------------------------------------------- |
| 302       | Found              | 일시적 리다이렉션: 재요청 메서드 변경될 수 있음 |
| 303       | See Other          | 일시적 리다이렉션: 재요청 메서드 GET으로 변경   |
| 307       | Temporary Redirect | 일시적 리다이렉션: 재요청 메서드 변경되지 않음  |

#### 400번대: 클라이언트 에러 상태 코드

- 클라이언트에 의한 에러가 있음을 알려주는 상태 코드

| 상태 코드 | 이유 구문          | 설명                                                  |
| --------- | ------------------ | ----------------------------------------------------- |
| 400       | Bad Request        | 클라이언트의 요청이 잘못되었음                        |
| 401       | Unauthorized       | 요청한 자원에 대한 유효한 인증이 없 음                |
| 403       | Forbidden          | 요청이 서버에 의해 거부됨 (ex) 접근 권한이 없을 경우) |
| 404       | Not Found          | 요청받은 자원을 찾을 수 없음                          |
| 405       | Method Not Allowed | 요청한 메서드를 지원하지 않음                         |

- 서버가 상태 코드 401 (Unauthorize)로 응답할 때는 반드시 'WWW-Authenticate'라는 헤더를 통해 인증 방법을 알려주어야 함
- 인증: 자신이 누군지 증명하는 것
- 인가 (권한 부여): 인증된 주체에게 작업을 허용하는 것
- 상태 코드 404 (Not Found)는 접근하고자 하는 자원이 존재하지 않거나 존재하더라도 공개하지 않는 자원에 대해 응답함

#### 500번대: 서버 에러 상태 코드

- 서버 에러에 대한 상태 코드

| 상태 코드 | 이유 구문             | 설명                                                 |
| --------- | --------------------- | ---------------------------------------------------- |
| 500       | Internal Server Error | 요청을 처리할 수 없음                                |
| 502       | Bad Gateway           | 중간 서버의 통신 오류                                |
| 503       | Service Unavailable   | 현재는 요청을 처리할 수 없으나 추후 가능할 수도 있음 |

- 상태 코드 500 (Internal Server Error)는 서버의 예기치 못한 상황으로 인해 요청을 처리할 수 없음을 나타내는 상태 코드임 (서버 내 에러를 통칭)
- 상태 코드 503 (Service Unavailable)는 현재 서비스를 일시적으로 이용할 수 없음을 의미하는 상태 코드 (서버가 과부하 상태에 있거나 일시적인 점검 상태일 때)

### cf) HTTP의 발전: HTTP/0.9에서 HTTP/3.0까지

#### 1. HTTP/0.9

- 지금은 거의 사용되지 않는 초창기 HTTP 버전
- 사용 가능한 메서드는 GET 뿐임
- 요청 메시지는 한 줄로 구성
- 헤더가 지원되지 않음

#### 2. HTTP/1.0

- HEAD, POST와 같은 GET 이외의 메서드가 도입됨
- 헤더 지원
- 지속 연결은 지원하지 않음

#### 3. HTTP/1.1

- 지속 연결을 지원
- 특정 요청에 대한 응답이 수신되기 전에 다음 요청을 보낼 수 있는 파이프라이닝 기능을 지원함
- 콘텐츠 협상 기능 등 다양한 헤더가 추가됨
- 오늘날 널리 사용되는 버전임
- 단점: HOL(Head-Of-Line) 블로킹 문제가 있음
  - HOC 블로킹: 같은 큐에 대기하며 순차적으로 처리되는 여러 패킷이 있을 때, 첫 번째 패킷의 처리 지연으로 인해 나머지 패킷들의 처리도 모두 지연되는 문제 상황

#### 4. HTTP/2.0

- HTTP/1.1의 효율과 성능을 높인 버전
- 송수신 효울을 높이기 위해 헤더를 압축하여 전송
- (텍스트 기반의 메시지를 송수신한 이전 버전과는 달리) 바이너리 데이터 기반의 메시지를 송수신함
- 클라리언트가 요청하지 않았더라도 미래에 필요할 것으로 예상되는 자원을 미리 전송해주는 '서버 푸시' 기능을 제공함
- 멀티플렉싱 기법을 도입해 HTTP/1.1의 HOL 블로킹 문제를 완화함
  - 멀티플렉싱 기법: 여러 스트림을 이용해 병렬적으로 메시지를 주고받는 기술
  - 요청과 응답을 주고받는 단위는 하나의 스트림에서 이루어지고, 이러한 스트림을 여러 개 활용하는 동시에 스트림별로 독자적인 송수신이 가능하며, 스트림별로 메시지들은 꼭 일정한 순서를 유지할 필요가 없음

#### 5. HTTP/3.0

- 이전까지의 HTTP 버전과는 달리 UDP를 기반으로 동작함
- 정확히는 UDP를 기반으로 구현된 QUIC (Quick UDP Internet Connections) 프로토콜을 기반으로 동작함
- UDP는 TCP에 비해 상대적으로 빠르기 때문에, 속도 측면에서 큰 개선이 이루어짐

## 3️⃣ HTTP 헤더와 HTTP 기반 기술

- HTTP 헤더는 필드 이름(헤더 이름)과 필드 값(헤더 값)이 콜론을 기준으로 구분되어 있음

### HTTP 헤더

#### 요청 시 활용되는 HTTP 헤더

##### 1. Host

- 요청을 보낼 호스트를 나타내는 헤더
- 주로 도메인 네임으로 명시되며, 포트 번호가 포함되어 있을 수 있음

##### 2. User-Agent

- 웹 브라우저와 같이 HTTP 요청을 시작하는 클라이언트 측의 프로그램
- 운영 체제, 브라우저 종류 및 버전, 렌더링 엔진 등의 정보가 포함됨

##### 3. Referer

- 클라이언트가 요청을 보낼 때 머무르고 있던 URL

##### 4. Authorization

- 클라이언트의 인증 정보를 담는 헤더
- 인증 타입과 인증을 위한 정보가 차례로 명시됨

  ```
  Authorization: <type> <credentials>
  ```

- Basic 타입 인증: 'username:password' 같이 사용자 아이디와 비밀번호를 콜론을 이용해 합친 뒤, 이를 Base 64 인코딩한 값으로 인증 정보를 삼는 방식

#### 응답 시 활용되는 HTTP 헤더

##### 1. Server

- 서버 측의 소프트웨어와 관련된 정보

##### 2. Allow

- 클라이언트에게 허용된 HTTP 메서드 목록
- 상태 코드 405(Method Not Allowed)를 응답하는 메시지에서 함께 사용됨

##### 3. Retry-After

- 자원을 사용할 수 있는 날짜 혹은 시각
- 상태 코드 503(Service Unavailable)를 응답하는 메시지에서 함께 사용됨

##### 4. Location

- 클라리언트에게 자원의 위치를 알려 주기 위해 사용되는 헤더
- 주로 리다이렉션이 발생했을 때나 새로운 자원이 생성되었을 때 사용

##### 5. WWW-Authenticate

- 자원에 접근하기 위한 인증 방식(type)을 설명하는 헤더
- 보안 영역(realm)을 함께 알려 주거나 인증에 사용될 문자 집합도 알려줄 수 있음
- 상태 코드 401(Unauthorized)를 응답하는 메시지에서 함께 사용됨

#### 요청과 응답 모두에서 활용되는 HTTP 헤더

##### 1. Date

- 메시지가 생성된 날짜와 시각

##### 2. Connection

- 클라이언트의 요청과 응답 간의 연결 방식을 설정하는 헤더
- `Connection: keep-alive`: 지속 연결을 희망할 때 사용
- `Connection: close`: 연결을 종료하고 싶을 때 사용

##### 3. Content-Length

- 본문의 바이트 단위 크기(길이)

##### 4. Content-Type, Content-Language, Content-Encoding

- 전송하려는 메시지 본문의 표현 방식을 설명하는 헤더
- 표현 헤더(representation header)의 일종
- Content-Type 헤더: 메시지 본문에서 사용된 미디어 타입

  ```
  Content-Type: text/html; charset=UTF-8
  ```

- Content-Language 헤더: 메시지 본문에 사용된 자연어

  - 언어 태그로 명시 되며, 언어 태그는 하이픈으로 구분됨
  - 첫 번째 서브 태그는 언어 코드이고, 두 번째 서브 태그는 국가 코드임
  - ex) ko-KR, en-US, en-GB

- Content-Encoding 헤더: 메시지 본문을 압축하거나 변환한 방식
  - ex) gzip, compress, deflate, br

### 캐시

- 불필요한 대역폭 낭비와 응답 지연을 방지하기 위해 정보의 사본을 임시로 저장하는 기술
- 동일한 요청에 대해 캐시된 데이터를 활용할 수 있기 때문에 불필요한 대역폭 낭비를 줄일 수 있고, 더 빠르게 데이터에 접근할 수 있음
- 캐시는 웹 브라우저에 저장(개인 전용 캐시)되어 있기도 하고, 클라이언트와 서버 사이에 위치한 중간 서버에 저장(공용 캐시)되어 있기도 함

#### 캐시 신선도

- 캐시 신선도: 캐시된 사본 데이터가 얼마나 최신 데이터와 유사한지 정도
- 캐시를 했다면 항상 캐시한 이후로 원본 데이터가 변경되는 상황에 대비해야 함
- 캐시 데이터에 유효 기간을 설정하고, 기간이 만료되었다면 원본 데이터를 다시 요청하는 방식으로 캐시 신선도를 유지할 수 있음
- 캐시할 데이터에 유효 기간을 부여하는 방법으로 응답 메시지의 `Expires` 헤더(날짜)와 `Cache-Control` 헤더의 Max-Age 값(초)을 사용할 수 있음
- 캐시의 유효 기간이 만료된 후, 캐시된 자원이 여전히 최신 상태의 정보인지 재검사하는 방법에는 두 가지가 있음
  1.  날짜를 기반으로 서버에게 물어보는 방법
  2.  엔티티 태그를 기반으로 서버에게 물어보는 방법

##### 1. 날짜를 기반으로 캐시의 신선도 재검사

- 클라이언트는 `If-Modified-Since` 헤더를 통해 서버에게 특정 시점 이후로 원본 데이터에 변경 있었는지 물어볼 수 있음

1. 요청받은 자원이 변경된 경우

   - 서버는 상태 코드 200(OK)과 함께 새로운 자원을 반환해줌

2. 요청받은 자원이 변경되지 않은 경우

   - 서버는 상태 코드 304(Not Modified)를 응답하는 메시지를 보냄
   - 응답 메시지에 `Last-Modified` 헤더를 포함해, 클라이언트에게 자원의 마지막 변경 시점을 알려줌

3. 요청받은 자원이 삭제된 경우

   - 서버는 상태 코드 404(Not Found)를 응답하는 메시지를 보냄

##### 2. 엔티티 태그를 기반으로 캐시의 신선도 재검사

- Entity Tag(Etag): '자원의 버전'을 식별하기 위한 정보
- 자원이 변경될 때마다 자원의 버전을 식별하는 Etag 값이 변경됨
- 클라이언트는 `If-None-Match` 헤더를 통해 서버에게 캐시된 자원의 Etag 값과 일치하는 자원이 있는지 물어볼 수 있음

1. 요청받은 자원이 변경된 경우(Etag 값이 변경됨)

   - 서버는 상태 코드 200(OK)과 함께 변경된 데이터와 Etag 값을 응답함

2. 요청받은 자원이 변경되지 않은 경우(Etag 값이 동일함)

   - 서버는 상태 코드 304(Not Modified)를 응답하는 메시지를 보냄

3. 요청받은 자원이 삭제된 경우

   - 서버는 상태 코드 404(Not Found)를 응답하는 메시지를 보냄

### 쿠키

- 서버에서 생성되어 클라이언트 측에 저장되는 데이터
- 상태를 유지하지 않는 HTTP의 특성을 보완하기 위한 수단
- 서버는 쿠키를 생성해서 클라이언트에게 전송하고, 클라이언트는 전달받은 쿠키를 저장해 두었다가 추후 동일한 서버에 보내는 요청 메시지에 쿠키를 포함해 전송함
- 서버는 쿠키 정보를 참고해 두 개의 요청이 같은 클라이언트에서 왔는지, 로그인 상태를 유지하고 있는지 등을 알 수 있음

#### cf) 세션 인증

- 쿠키를 통해 세션 아이디를 전송하면 요청을 보낼 때마다 인증 과정을 거칠 필요가 없어 효율적임

1. 클라이언트는 서버에게 (아이디, 비밀번호와 같은) 인증 정보를 전송함
2. 인증 정보가 올바르다면, 서버는 세션 아이디를 생성해 클라이언트에게 전송함
3. 서버는 생성한 세션 아이디를 데이터베이스 등에 저장함
4. 클라이언트는 추후 요청을 보낼 때 쿠키 내에 세션 아이디를 포함해 전송함
5. 서버는 쿠키 속 세션 아이디와 저장된 세션 아이디를 비교하여 클라이언트를 식별함

#### 쿠키 관련 헤더

- 응답 메시지의 `Set-Cookie` 헤더와 요청 메시지의 `Cookie` 헤더를 통해 전달됨
- 응답 메시지

  ```
  Set-Cookie: 이름=값; 속성1; 속성2
  ```

  ```
  Set-Cookie: name=minchul
  Set-Cookie: phone=100-100
  Set-Cookie: message=Hello
  ```

- 요청 메시지

  ```
  Cookie: 이름=값; 이름=값;
  ```

  ```
  Cookie: name=minchul; phone=100-100; message=Hello
  ```

#### 쿠키 관련 속성

- domain: 쿠키가 적용될 도메인

  ```
  Set-Cookie: name=minchul domain=example.com
  ```

- path: 쿠키가 적용될 경로

  - path로 지정된 경로와 하위 경로에서 해당 쿠키 정보를 활용할 수 있음

  ```
  Set-Cookie: name=minchul path=/lectures
  ```

- Expires: 쿠키 만료 시점

  - 형식: 요일, DD-MM-YY HH:MM:SS GMT
  - 이 시점이 지나면 해당 쿠키는 삭제되어 전달되지 않음

  ```
  Set-Cookie: sessionID=abc123; Expires=Fri, 23 Aug 2024 09:00:00 GMR
  ```

- Max-Age: 초 단위 유효 기간

  - 이 기간이 지나면 해당 쿠키는 삭제되어 전달되지 않음

  ```
  Set-Cookie: sessionID=abc123; Max-Age=2592000
  ```

- Secure: HTTPS 프로토콜이 사용되는 경우에만 쿠키를 전송
- HttpOnly: HTTP 송수신을 통해서만 쿠키를 이용하도록 제한
  - 즉, 자바스크립트에서 쿠키에 접근하지 못하도록 함

#### cf) 웹 스토리지: 로컬 스토리지와 세션 스토리지

- 웹 브라우저 내의 저장 공간
- 클라이언트의 상태를 추측할 수 있는 <키-값> 쌍 형태의 정보를 저장함
- 세션 스토리지: 세션이 유지되는 동안(브라우저가 열려있는 동안) 유지되는 정보
- 로컬 스토리지: 별도로 삭제하지 않는 한 영구적으로 저장이 가능한 정보
- 쿠키와의 차이점
  1. 일반적으로 쿠키보다 더 큰 데이터를 저장할 수 있음
  2. 쿠키는 서버로 자동 전송되지만, 웹 스토리지의 정보는 서버로 자동 전송되지 않음

### 콘텐츠 협상과 표현

- 콘텐츠 협상: 같은 URI에 대해 가장 적합한 '자원의 형태'를 제공하는 메커니즘
- 자원의 표현: 송수신 가능한 자원의 형태
- 같은 URI로 식별 가능한 HTML 문서라 해도, 영어로 요청하면 영어로 된 형태로 제공하고, 한국어로 요청하면 한국어로 된 형태를 제공함
- 다시 말해, GET 메서드를 정확히 말하면 '자원의 특정 표현을 습득하기 위한 메서드'라고 정의할 수 있음

#### 콘텐츠 협상 관련 헤더

- Accept: 선호하는 미디어 타입
- Accept-Language: 선호하는 언어
- Accept-Charset: 선호하는 문자 인코딩 방식
- Accept-Encoding: 선호하는 압축 방식
- q 값을 통해 선호도에 대한 우선순위를 표현할 수 있음

  - 범위는 0부터 1까지
  - 값이 클수록 우선순위가 높음
  - 생략되었을 경우에는 1을 의미함

  ```
  Accept-Language: ko-Kr,ko;q=0.9,en-US;q=0.8,en;q=0.7
  Accept: text/html,application/xml;q=0.9,text/plain;q=0.6,*/*;q=0.5
  ```
