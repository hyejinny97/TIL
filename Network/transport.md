# ✔ 전송 계층

## 1️⃣ 전송 계층의 개요: IP의 한계와 포트

### 신뢰할 수 없는 통신과 비연결형 통신

- IP는 비신뢰성 프로토콜이자 비연결형 프로토콜임
- 비신뢰성 통신: 패킷이 수신지까지 제대로 전송되었다는 보장을 하지 않음 (최선형 통신)

### IP의 한계를 보완하는 전송 계층

- TCP: 연결형/신뢰형 프로토콜
- UDP: 비연결형/비신뢰형 프로토콜
  - TCP보다 비교적 빠른 전송이 가능함

#### 1. 전송 계층은 연결형 통신을 가능하게 함

- TCP는 송수신하는 동안 연결을 유지하고, 송수신이 끝나면 연결을 종료함

#### 2. 전송 계층은 신뢰성 있는 통신을 가능하게 함

- TCP는 패킷이 수신지까지 올바른 순서대로 확실이 전달되는 것을 보장하기 위해 재전송을 통한 오류 제어, 흐름 제어, 혼잡 제어 등 다양한 기능들을 제공함

### 응용 계층과의 연결 다리, 포트

#### 포트의 정의

- 패킷은 실행 중인 특정 애플리케이션 프로세스까지 전달되어야 함
- 포트(port): 특정 애플리케이션을 식별할 수 있는 정보
- 포트 번호를 사용하면, 패킷 내 수신지 포트와 송신지 포트를 통해 송수신지 호스트의 애플리케이션을 식별할 수 있음
- TCP와 UDP 모두 송수신지 포트 번호를 포함함
- 아래는 특정 호스트에서 실행 중인 특정 애플리케이션 프로세스를 의미함

  ```
  IP 주소:포트 번호
  ```

#### 포트의 분류

- 포트 번호는 16비트로 표현 가능

  - 따라서, 사용 가능한 포트의 수는 2^16(65536)

  | 포트 종류      | 포트 번호 범위 |
  | -------------- | -------------- |
  | 잘 알려진 포트 | 0 ~ 1023       |
  | 등록된 포트    | 1024 ~ 49151   |
  | 동적 포트      | 49152 ~ 65535  |

- 잘 알려진 포트와 등록된 포트는 인터넷 할당 번호 관리 기관(IANA)라는 국제 단체에 의해 할당됨
- 서버로서 동작하는 프로그램은 일반적으로 잘 알려진 포트와 등록된 포트로 동작하는 경우가 많음
- 클라이언트(ex) 웹 브라우저)로서 동작하는 프로그램은 동적 포트 중에서 임의의 번호가 할당되는 경우가 많음
- 아래 포트 번호는 권고일 뿐이며, 강제 사항은 아님

##### 1. 잘 알려진 포트 (Well Known Port)

- 범용적으로 사용되는 애플리케이션 프로토콜이 일반적으로 사용하는 유명한 포트 번호

  | 잘 알려진 포트 번호 | 설명   |
  | ------------------- | ------ |
  | 20, 21              | FTP    |
  | 22                  | SSH    |
  | 23                  | TELNET |
  | 53                  | DNS    |
  | 67, 68              | DHCP   |
  | 80                  | HTTP   |
  | 443                 | HTTPS  |

##### 2. 등록된 포트 (Registered Port)

- 흔히 사용되는 애플리케이션 프로토콜에 할당하기 위해 사용됨

  | 등록된 포트 번호 | 설명                              |
  | ---------------- | --------------------------------- |
  | 1194             | OpenVPN                           |
  | 1433             | Microsoft SQL Server 데이터베이스 |
  | 3306             | MySQL 데이터베이스                |
  | 6379             | Redis                             |
  | 8080             | HTTP 대체                         |

##### 3. 동적 포트 (Dynamic Port)

- 사설 포트, 임시 포트라고도 불림
- 인터넷 할당 번호 관리 기관에 의해 할당된 애플리케이션 프로토콜이 없음
- 특별히 관리되지 않는 포트 번호인 만큼 자유롭게 사용 가능

### 포트 기반 NAT

- NAT: IP 주소를 변환하는 기술
  - 주로 네트워크 내부에서 사용되는 사설 IP 주소와 외부에서 사용되는 공인 IP 주소를 변환하는데 사용됨

#### NAT 변환 테이블

- 사설 IP 주소와 공인 IP 주소가 일대일로 대응된다면, 네트워크 내부에서 사용되는 사설 IP 주소의 수만큼 공인 IP 주소가 필요하기 때문에 무리가 있음
- 오늘날 NAT 기술은 대부분 다수의 사설 IP 주소를 그보다 적은 수의 공인 IP 주소로 변환함

#### NAPT

- Network Address Port Translation
- 포트 기반의 NAT
- 포트를 활용해 하나의 공인 IP 주소를 여러 사설 IP 주소가 공유할 수 있도록 함
- NAT 테이블에 변환할 IP 주소 쌍과 더불어 포트 번호도 함께 기록됨
- 이를 통해, 공인 IP 주소 수 부족 문제를 개선할 수 있게 됨

### cf) 포트 포워딩

- Port Forwarding
- 특정 IP 주소와 포트 번호 쌍을 특정 호스트에게 할당한 뒤, 외부에서 통신을 시작할 호스트에게 해당 접속 정보(IP 주소:포트 번호 쌍)을 알려주는 기능
- 주로 네트워크 외부에서 네트워크 내부로 통신을 시작할 때, 네트워크 내부의 서버를 외부에서 접속할 수 있도록 접속 정보를 공개하기 위해 사용됨

### cf) ICMP

- Internet Control Message Protocol
- IP의 비신뢰형/비연결형 전송 특성을 보완하기 위한 네트워크 계층의 프로토콜
- IP 패킷의 전송 과정에 대한 피드백 메시지(ICMP 메시지)를 얻기 위해 사용되는 프로토콜
- 주의) ICMP가 IP의 신뢰성을 보장하는 것은 아님
  - 신뢰성 보장을 위해선 전송 계층의 프로토콜이 필요

#### ICMP 메시지 헤더 구조

- 타입(type) + 코드(code)
- 타입: ICMP 메시지의 유형이 번호로 명시되는 필드
- 코드: 구체적인 메시지 내용이 번호로 명시되는 필드

#### ICMP 메시지 종류

##### 1. 전송 과정에서 발생한 문제 상황에 대한 오류 보고

| 타입 이름 (타입 번호) | 코드 설명 (코드 번호)                                    |
| --------------------- | -------------------------------------------------------- |
| 수신지 도달 불가 (3)  | 네트워크 도달 불가 (0)                                   |
| 수신지 도달 불가 (3)  | 호스트 도달 불가 (1)                                     |
| 수신지 도달 불가 (3)  | 프로토콜 도달 불가,수신지에서 특정 프로토콜 사용 불가(2) |
| 수신지 도달 불가 (3)  | 포트 도달 불가 (3)                                       |
| 수신지 도달 불가 (3)  | 단편화가 필요하지만 DF가 1로 설정되어 단편화 불가 (4)    |
| 시간 초과 (11)        | TTL 만료 (0)                                             |

##### 2. 네트워크에 대한 진단 정보

| 타입 이름 (타입 번호) | 코드 설명 (코드 번호)                            |
| --------------------- | ------------------------------------------------ |
| 에코 요청 (8)         | 에코 요청 (0)                                    |
| 에코 응답 (0)         | 에코 요청에 대한 응답 (0)                        |
| 라우터 광고 (9)       | 라우터 광고, 라우터가 호스트에게 자신을 알림 (0) |

## 2️⃣ TCP와 UDP

- TCP (Transmission Control Protocol): 연결형/신뢰형 프로토콜
- UDP (User Datagram Protocol): 비연결형/비신뢰형 프로토콜
  - TCP보다 신뢰성은 떨어지지만, 비교적 빠른 통신이 가능

### TCP 통신 단계와 세그먼트 구조

- TCP 통신 단계
  1. 연결 수립
  2. 데이터 송수신 (재전송을 통한 오류 제어, 흐름 제어, 혼잡 제어)
  3. 연결 종료
- MSS (Maximum Segment Size): TCP로 전송할 수 있는 최대 페이로드 크기
  - TCP 헤더 크기는 제외
- TCP 세그먼트 헤더 구조
  - 송신지 포트, 수신지 포트
  - 순서 번호
  - 확인 응답 번호
  - 제어 비트
  - 윈도우

#### 제어 비트

- 기본적으로 8비트로 구성
- `ACK`: 세그먼트의 승인을 나타내기 위한 비트
- `SYN`: 연결을 수립하기 위한 비트
- `FIN`: 연결을 종료하기 위한 비트

#### 순서 번호와 확인 응답 번호

- TCP의 신뢰성을 보장하기 위해 사용되는 중요한 필드

##### 순서 번호

- 세그먼트의 올바른 송수신 순서를 보장하기 위한 번호
- MSS 크기만큼 쪼개진 각 세그먼트 데이터의 첫 4 바이트에 부여되는 번호
- 초기 순서 번호: SYN 플래그가 1로 설정된 세그먼트에서 무작위 값을 가진 순서 번호
- 순서 번호 = 초기 순서 번호 + 송신한 바이트 수(떨어진 바이트 수)

##### 확인 응답 번호

- 순서 번호에 대한 응답
- 수신자가 다음으로 받기를 기대하는 순서 번호
- 일반적으로 '수신한 순서 번호 + 1'로 설정됨
- 확인 응답 번호 값을 보내기 위해서, ACK 플래그를 1로 설정해야 함

### TCP 연결 수립과 종료

#### 연결 수립: Three-way Handshake

| 송수신 방향 | 세그먼트               | 세그먼트에 포함된 주요 정보                                                                                                               | 비유                               |
| ----------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| A → B       | `SYN` 세그먼트         | - 호스트 A의 초기 순서 번호<br />- 1로 설정된 SYN 비트                                                                                    | '연결 시작합니다.'                 |
| B → A       | `SYN` + `ACK` 세그먼트 | - 호스트 B의 초기 순서 번호<br />- 호스트 A가 전송한 세그먼트에 대한 확인 응답 번호<br />- 1로 설정된 SYN 비트<br />- 1로 설정된 ACK 비트 | '네, 확인했습니다. 연결 시작해요!' |
| A → B       | `ACK` 세그먼트         | - 호스트 A의 다음 순서 번호<br />- 호스트 B가 전송한 세그먼트에 대한 확인 응답 번호<br />- 1로 설정된 ACK 비트                            | '네, 확인했습니다.'                |

- 3개의 단계로 이루어진 TCP의 연결 수립 과정
- 액티브 오픈: 처음 연결을 요청하는 호스트의 연결 수립 과정
  - 주로, 클라이언트에 의해 수행됨
- 패시브 오픈: 연결 요청을 받고 나서 연결을 수립하는 호스트의 연결 수립 과정
  - 주로, 서버에 의해 수행됨

#### 연결 종료: Four-way Handshake

| 송수신 방향 | 세그먼트       | 세그먼트에 포함된 주요 정보                                                   | 비유                |
| ----------- | -------------- | ----------------------------------------------------------------------------- | ------------------- |
| A → B       | `FIN` 세그먼트 | - 1로 설정된 FIN 비트                                                         | '연결 끊을게요.'    |
| B → A       | `ACK` 세그먼트 | - 호스트 A가 전송한 세그먼트에 대한 확인 응답 번호<br />- 1로 설정된 ACK 비트 | '네, 확인했습니다.' |
| B → A       | `FIN` 세그먼트 | - 1로 설정된 FIN                                                              | '이제 연결 끊어요.' |
| A → B       | `ACK` 세그먼트 | - 호스트 B가 전송한 세그먼트에 대한 확인 응답 번호<br />- 1로 설정된 ACK 비트 | '네, 확인했습니다.' |

- 4개의 단계로 이루어진 TCP의 연결 종료 과정
- 액티브 클로즈: 먼저 연결을 종료하려는 호스트에 의해 수행됨
- 패시브 클로즈: 연결 종료 요청을 받아들이는 호스트에 의해 수행됨

### TCP 상태

- 상태 (state): 현재 어떤 통신 과정에 있는지를 나타내는 정보
- TCP는 상태를 유지하고 활용한다는 점에서 스테이트풀(stateful) 프로토콜라고도 불림

#### 연결이 수립되지 않은 상태

- `CLOSED`: 아무런 연결이 없는 상태
- `LISTEN`: 연결 대기 상태 (SYN 세그먼트를 기다리는 상태)
  - 일반적으로, 서버로서 동작하는 패시브 오픈 호스트가 LISTEN 상태를 유지함

#### 연결 수립 상태

- `SYN-SENT`: 액티브 오픈 호스트가 SYN 세그먼트를 보낸 뒤 그에 대한 응답인 SYN + ACK 세그먼트를 기다리는 상태
- `SYN-RECEIVED`: 패시브 오픈 호스트가 SYN + ACK 세그먼트를 보낸 뒤, 그에 대한 ACK 세그먼드를 기다리는 상태
- `ESTABLISHED`: 두 호스트가 각자 ACK 세그먼트를 주고 받아, 연결이 확립된 상태 (데이터를 송수신할 수 있는 상태)

#### 연결 종료 상태

- `FIN-WAIT-1`: 액티브 클로즈 호스트가 FIN 세그먼트를 보낸 뒤 그에 대한 응답인 ACK 세그먼트를 기다리는 상태
- `CLOSE-WAIT`: 패시브 클로즈 호스트가 ACK 세그먼트를 보낸 후 대기하는 상태
- `FIN-WAIT-2`: 액티브 클로즈 호스트가 ACK 세그먼트를 받은 후, FIN 세그먼트를 기다리는 상태
- `LAST-ACK`: 패시브 클로즈 호스트가 FIN 세그먼트를 보낸 후, 이에 대한 ACK 세그먼트를 기다리는 상태
- `TIME-WAIT`: 액티브 클로즈 호스트가 FIN 세그먼트를 받고, ACK 세그먼트를 보낸 후 일정 시간동안 접어드는 상태
- 패시브 클로즈 호스트는 마지막 ACK 세그먼트를 받은 후 바로 CLOSED 상태로 전이되는 반면, 액티브 클로즈 호스트는 TIME-WAIT 상태에서 일정 시간 기다린 뒤 CLOSED 상태로 전이됨
- 이유: 패시브 클로즈 호스트가 마지막 ACK 세그먼트가 올바르게 전송되지 않았다면, 해당 세그먼트를 재전송해야하기 때문에 TIME-WAIT 상태로 일정 시간 대기한 후 CLOSED 상태로 접어듬
- `CLOSING` 상태: 보통 두 호스트가 동시에 연결을 종료하려할 때 전이되는 상태

### UDP 데이터그램 구조

- 상태를 유지하지도 활용하지도 않아서 스테이트리스(stateless) 프로토콜로도 불림
- UDP 데이터그램 헤더 구조
  - 송신지 포트, 수신지 포트
  - 길이
  - 체크섬: 전송 과정에서 오류가 발생했는지 검사하기 위한 필드
- UDP는 TCP에 비해 패킷을 빠르게 처리할 수 있음
- 따라서, 주로 실시간 스트리밍 서비스, 인터넷 전화처럼 실시간성이 강조되는 상황에서 많이 쓰임
- 수신지에 패킷들을 빠르게 마구 던지는 과정에서 패킷이 손실되거나 패킷의 순서가 바뀔 수도 있음

## 3️⃣ TCP의 오류.흐름.혼잡 제어

- TCP는 재전송을 기반으로 다양한 오류를 제어하고, 흐름 제어를 통해 처리할 수 있는 만큼의 데이터만을 주고받으며, 혼잡 제어를 통해 네트워크가 혼잡한 정도에 따라 전송량을 조절함

### 오류 제어: 재전송 기법

#### 오류 검출

- 체크섬은 세그먼트의 훼손 여부만 나타낼 뿐이고, 이를 통해 전송 과정에 문제가 있음을 전부 감지할 순 없음
  - 체크섬 값이 잘못되었다면 호스트는 해당 패킷을 읽지 않고 폐기함
- TCP가 오류를 검출하고 세그먼트를 재전송하는 상황
  1. 중복된 ACK 세그먼트를 수신했을 때
  2. 타임아웃이 발생했을 때
- RTT (Round Trip Time): 메시지를 전송한 뒤 그에 대한 답변을 받는데까지 걸리는 시간
- 호스트는 세그먼트를 전송할 때마다 재전송 타이머를 시작하는데, ACK 세그먼트를 받지 못해 타이머의 카운트다운이 끝난 상황을 타임아웃이라고 함

#### 재전송 기법

- ARQ (Automatic Repeat Request): 문제가 생긴 메시지를 재전송함으로써 신뢰성을 확보하는 방식
  - Stop-and-Wait ARQ
  - Go-Back-N ARQ
  - Selective Repeat ARQ

##### Stop-and-Wait ARQ

- 제대로 전달했음을 확인하기 전까지는 새로운 메시지를 보내지 않는 방식
- 단순하지만, 높은 신뢰성을 보장함
- 단점: 네트워크의 이용 효율이 낮아지고, 이는 성능 저하로 이어짐

##### Go-Back-N ARQ

- 파이프라이닝(pipelining): 연속해서 메시지를 전송할 수 있는 기술
  - Go-Back-N ARQ와 Selective Repeat ARQ는 파이프라이닝을 사용함
- 파이프라이닝 방식을 활용해 여러 세그먼트를 전송하고, 도중에 잘못 전송된 세그먼트가 발생할 경우 해당 세그먼트부터 전부 다시 전송하는 방식
- 즉, 순서 번호 n번에 대한 ACK 세그먼트는 'n번까지의' 확인 응답이라고 볼 수 있기 때문에, Go-Back-N ARQ의 ACK 세그먼트를 누적 확인 응답이라고 함

##### Selective Repeat ARQ

- 수신 호스트 측에서 제대로 전송받은 각각의 패킷들에 대해 ACK 세그먼트를 보내는 방식
- 즉, Selective Repeat ARQ의 ACK 세그먼트를 개별 확인 응답이라고 함

##### cf) 빠른 재전송 (Fast Retransmit)

- 재전송 타이머가 만료되기 전이라도 세 번의 동일한 동일한 ACK 세그먼트가 수신되었다면 해당 세그먼트를 곧바로 재전송하는 기능
- 시간 낭비를 줄이며 빠르게 손실된 세그먼트를 재전송함으로써 성능을 높이는 기능임

### 흐름 제어: 슬라이딩 윈도우

- 호스트가 한 번에 받아서 처리할 수 있는 세그먼트의 양에는 한계가 있음
  - 수신 버퍼: 수신된 세그먼트가 애플리케이션 프로세스에 의해 읽히기 전에 임시로 저장되는 공간
  - 송신 호스트가 수신 버퍼의 크기보다 많은 데이터를 전송하면(버퍼 오버플로), 일부 세그먼트가 처리되지 못할 수 있음
- 따라서, 송신 호스트는 수신 호스트의 처리 속도를 고려하여 송수신 속도를 균일하게 유지해야 함
- 파이프라이닝을 사용해 연속해서 세그먼트를 전송하는 경우 호름 제어가 필요함
- 윈도우: 송신 호스트가 파이프라이닝할 수 있는 최대량
  - 윈도우 크기만큼 확인 응답을 받지 않고도 한 번에 전송 가능
- 슬라이딩 윈도우: 파이프라이닝 과정에서 송수신 윈도우가 오른쪽으로 미끄러지듯 움직이는 것
- TCP 세그먼트 내에 있는 윈도우 필드에는 수신 윈도우의 크기가 명시되고, 이는 한 번에 수신하고자하는 데이터의 양을 나타냄
- 수신 호스트는 TCP 헤더의 윈도우 필드를 통해 송신 호스트에게 한 번에 받을 수 있는 데이터의 양을 알리게 됨

### 혼잡 제어

- 혼잡: 많은 트래픽으로 인해 패킷의 처리 속도가 늦어지거나 유실될 우려가 있는 네트워크 상황
- 송신 호스트는 네트워크 혼잡도를 판단하고 혼잡한 정도에 맞춰 유동적으로 전송량을 조절하며 전송함
- 혼잡 윈도우: 혼잡 없이 전송할 수 있을 법한 데이터양
- 혼잡 윈도우의 크기는 송신 호스트가 혼잡 제어 알고리즘을 통해 직접 계산해야 함

#### AIMD

- Additive Increase/Multiplicative Decrease
- 합으로 증가, 곱으로 감소
- 혼잡이 감지되지 않는다면 혼잡 윈도우를 RTT마다 1씩 선형적으로 증가시키고, 혼잡이 감지되면 혼잡 윈도우를 절반으로 떨어뜨리는 동작을 반복하는 알고리즘

#### 느린 시작 알고리즘

- 혼잡 윈도우를 1부터 시작해 문제없이 수신된 ACK 세그먼트 하나당 1씩 증가하는 방식
- 즉, 혼잡 윈도우는 RTT마다 2배씩 지수적으로 증가함
- 혼잡 윈도우 값이 계속 증가하다가 아래 세 종류의 혼잡이 감지되면 다음과 같은 방법을 선택하게 됨

  | 상황 분류                       | 방법                                                                                                                   |
  | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
  | 타임아웃 발생                   | 혼잡 윈도우 값을 1로, 느린 시작 임계치를 혼잡이 감지되었을 시점의 혼잡 윈도우 값의 절반으로 초기화한 뒤 느린 시작 재개 |
  | 혼잡 윈도우 >= 느린 시작 임계치 | 느린 시작 종료, 혼잡 윈도우를 절반으로 초기화한 뒤 혼잡 회피 수행                                                      |
  | 세 번의 중복 ACK 발생           | (빠른 재전송 후) 빠른 회복 수행                                                                                        |

#### 혼잡 회피 알고리즘

- RTT마다 혼잡 윈도우를 1MSS(Maximum Segment Size)씩 증가시키는 알고리즘
- 즉, 혼잡 윈도우 크기는 선형적으로 증가함

#### 빠른 회복 알고리즘

- 세 번의 중복 ACK 세그먼트를 수신했을 때 느린 시작은 건너뛰고 혼잡 회피를 수행하는 알고리즘

### cf) ECN: 명시적 혼잡 알림

- Explicit Congestion Notification
- 네트워크 중간 장치(주로 라우터)의 도움을 받아 송신 호스트가 빠르게 혼잡을 감지하고 혼잡 윈도우를 조절할 수 있음
- ECN을 지원하는 호스트의 경우, IP 헤더와 TCP 헤더에 ECN 관련 필드가 추가됨
